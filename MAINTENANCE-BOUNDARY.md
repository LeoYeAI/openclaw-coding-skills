# Maintenance Boundary

This document defines when the repository is "good enough" and what kinds of work are still worth doing afterward.

## Good Enough Means

The repository is already good enough when all of these are true:

- core workflow skills are stable
- specialist skills cover the common high-risk and high-frequency task families
- references exist for the main failure-prone areas
- trigger matrix, examples, and ambiguity cases are present
- evaluation, live validation, and feedback-loop documents exist
- adopters can understand how to install, use, tune, and publish the repository

## Worthwhile Next Work

These are still high-value after the repository is "good enough":

- tuning based on real tasks
- adding examples for repeated real phrasing
- strengthening one high-risk reference when a real miss exposes a gap
- refining one boundary after an observed trigger error

## Low-Value Work

These usually have poor return once the repository reaches this stage:

- adding many more abstract documents without new evidence
- renaming or reorganizing files for aesthetics alone
- broad rewrites of trigger descriptions without observed failures
- expanding every skill equally instead of following real task pressure

## Rule

After this point, prefer evidence-driven maintenance over speculative expansion.
